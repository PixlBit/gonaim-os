# ADR-0002 — Postgres + pgvector بدل Graph Database

- **Status:** Accepted
- **Date:** 2026-08-22
- **Source:** Master Blueprint §6، §28.3، §28.4

## السياق

النموذج المعلوماتي كله علاقات: `Node ← relation → Node`. ATLAS شاشة شبكة كاملة،
والبيان الحاكم في §6 هو "العلاقات أهم من العناصر نفسها". هذا يغري باستخدام Neo4j
أو ما شابه.

لكن الحجم الحقيقي: **مستخدم واحد**، مئات الآلاف من الأحداث على مدى سنوات،
وعمق استعلام نادرًا ما يتجاوز 3 قفزات ("هذا المنتج ← بحث عنه ← اشتراك يجدد قريبًا").

## القرار

`entities` + `entity_relations` كجدولين في Postgres، مع `pgvector` للبحث الدلالي.
لا Graph Database في MVP ولا V1.

الاستعلامات متعددة القفزات تُنفذ بـ`WITH RECURSIVE` وبسقف عمق صريح
(`max_depth = 3` افتراضيًا) لمنع انفجار الشبكة.

البحث النهائي **Hybrid** وليس vector-only:

```text
score = 0.35 × vector_similarity
      + 0.25 × keyword_rank (tsvector)
      + 0.20 × recency_decay
      + 0.20 × pinned_or_confirmed_boost
```

## النتائج

**إيجابية**
- قاعدة بيانات واحدة: entities، events، memories، embeddings، RLS، audit — كلها في مكان واحد بمعاملة واحدة.
- RLS في Supabase تحمي كل شيء بنفس الآلية؛ لا حاجة لتكرار نموذج الصلاحيات في محرك ثانٍ.
- `pgvector` يسمح بفلترة SQL قبل البحث الدلالي — نبحث داخل `sensitivity <= 'private'` فقط، وهو أمر يصعب في محرك vector منفصل.

**سلبية**
- استعلام شبكة عميق (5+ قفزات) سيكون أبطأ من Graph DB. مقبول: لا توجد حالة استخدام حقيقية تطلبه.
- تصور ATLAS يحتاج جلب subgraph ثم رسمه client-side بـCytoscape؛ لا يوجد محرك تخطيط في القاعدة.

**شرط الخروج من هذا القرار**
يُعاد النظر فقط إذا ظهر استعلام حقيقي متكرر بعمق > 4 قفزات وزمن استجابة > 400ms
بعد الفهرسة الصحيحة. غير ذلك، القرار يبقى.

## البدائل المرفوضة

| البديل | سبب الرفض |
| --- | --- |
| Neo4j / Memgraph | نظام ثانٍ للتشغيل والنسخ والصلاحيات، لمستخدم واحد وعمق 3 قفزات |
| Vector DB منفصل (Pinecone/Qdrant) | يفصل الـembedding عن الـsensitivity والـRLS — أخطر نقطة تسريب في التصميم |
| SQLite محلي فقط | يكسر الوصول من أكثر من جهاز موثوق، وهو متطلب في §1 |
