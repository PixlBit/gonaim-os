# ADR-0007 — الاستقلال لكل فعل، لا للنظام كله

- **Status:** Accepted
- **Date:** 2026-08-22
- **Source:** Expansion §11، §4.6؛ Master Blueprint §30.1

## السياق

النموذج الشائع: مفتاح واحد اسمه "AI autonomy" بين `off` و`full`. هذا خطأ هنا،
لأن غنيم قد يثق تمامًا في ARCHIVIST وهو يحفظ Backup يوميًا، ولا يثق إطلاقًا في
أي وكيل يلمس المال أو يرسل رسالة باسمه.

## القرار

الاستقلال **مصفوفة**، لا مفتاح. المفتاح هو `(agent, tool, source, sensitivity)`
والقيمة هي مستوى من ستة:

| المستوى | السلوك | مثال حقيقي |
| --- | --- | --- |
| **L0 — Mirror** | يرى ويعرض فقط | Money في MVP |
| **L1 — Suggest** | يقترح حركة | SCOUT يقترح فرصة |
| **L2 — Prepare** | يبني Draft أو Package | PRODUCER يجهز Reference Brief |
| **L3 — Execute with approval** | ينفذ بعد موافقة **كل مرة** | إرسال إيميل بعد Preview |
| **L4 — Bounded autonomy** | ينفذ داخل سياسة ضيقة | ARCHIVIST يحفظ Backup ليليًا |
| **L5 — Delegated domain** | يدير نطاقًا مع Audit | تنظيم Archive وفق قواعد معتمدة |

ولكل **Sense** أربعة مفاتيح منفصلة، لا مفتاح واحد (Expansion §4.6):

`can_observe` · `can_remember` · `can_infer` · `can_act`

هذا يسمح بالحالة المهمة: *"شوف الصفحة دي دلوقتي، بس متفتكرهاش ومتبعتهاش للسحابة."*

### سقف صلب لا يُتجاوز

بغض النظر عن أي إعداد، هذه الأفعال تبقى **L3 أو أقل إلى الأبد**:
شراء · دفع · نشر عام · إرسال باسم غنيم · حذف مصدر خارجي · تغيير صلاحية · تقديم على وظيفة.

الترقية من L3 إلى L4 لأي أداة تتطلب فعلًا بشريًا صريحًا في Control Room،
ولا يمكن أن يقترحها النظام على نفسه.

## النتائج

**إيجابية** — الثقة تُبنى تدريجيًا وبالدليل، وتُسحب جزئيًا دون تعطيل النظام كله.

**سلبية** — واجهة الصلاحيات تصبح أعقد. الحل: شاشة `PERMISSION MAP` تعرض المصفوفة بصريًا (من يرى / يتذكر / يستنتج / ينفذ)، لا قائمة مفاتيح طويلة.

## البدائل المرفوضة

| البديل | سبب الرفض |
| --- | --- |
| مفتاح واحد on/off | إما نظام أعمى أو نظام خطر — لا وسط |
| ثقة تتصاعد تلقائيًا مع نجاح الأفعال | النظام يمنح نفسه صلاحيات؛ تعارض مباشر مع GUARDIAN |
| أدوار جاهزة (`safe`/`balanced`/`power`) | تخفي أي أداة فُتحت فعلًا |
